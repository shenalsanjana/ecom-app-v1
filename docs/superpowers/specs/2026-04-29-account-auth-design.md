# Account, Auth, and Wishlist — Design

**Date:** 2026-04-29
**Status:** Approved for implementation planning
**Branch:** `develop`
**Scope:** Real authentication, profile management, saved addresses, wishlist, and password reset on top of the existing storefront scaffold. Storefront product/category data migrates from `mock.ts` into a local SQLite database.

> **2026-04-29 amendment:** Originally specified Postgres via Docker compose. Docker is not available on the target dev machine, so the database has been switched to **SQLite** (file-based, no server, no install). Affected sections: Stack additions, Data model (Decimal → Float), File layout (no `docker-compose.yml`), Environment variables (`DATABASE_URL` format).

This is **spec #1** of a five-spec sequence. The remaining specs (rate limiting, admin/RBAC, account deletion + data export, real cart/checkout/orders) are listed under [Future specs](#future-specs) and will be brainstormed in their own sessions after this spec is implemented.

## Goal

Add a real account area to the storefront. Users register and log in with email + password. Logged-in (registered) users get a profile page, an addresses section, a per-user wishlist, a static-mock orders page, and a working password-reset flow. Logged-out (guest) users continue to browse the storefront but see different header dropdown contents, and any attempt to reach `/account/*` or `/wishlist` redirects them to login. Storefront product and category data move into Postgres so that wishlist items have real referential integrity.

## Stack additions

On top of the existing scaffold (Next.js 16.2.4, React 19.2.4, Tailwind v4, shadcn/ui):

- **Auth.js v5** (`next-auth@5`) with the **Credentials provider** and **JWT session strategy** (`session: { strategy: "jwt" }`). The Auth.js Prisma adapter is *not* installed — Credentials does not use the adapter's session table.
- **Prisma + SQLite**. File-based DB at `prisma/dev.db` (gitignored). Connection: `DATABASE_URL="file:./dev.db"`. No external service, no install. The trade-off is no native `Decimal` column type — prices use `Float` (revisit when real money handling lands).
- **bcryptjs** for password hashing (pure JS, avoids the Edge-runtime native-binding issue that `bcrypt` hits).
- **zod** for input validation in server actions.
- **nodemailer** for password-reset emails over generic SMTP (host/user/pass/port/from in env).
- **shadcn primitives added**: `dropdown-menu` (profile menu, sidebar overflow), `label` (form fields), `dialog` (address-delete confirmation), `alert` (login success banner, action error/success messages). Existing primitives (`button`, `card`, `input`, `badge`, `separator`) stay.

Next 16 specifics that shape the design:

- The middleware file is renamed to `proxy.ts` in Next 16. We use `proxy.ts` at project root for route protection.
- Auth.js (NextAuth) is one of the libraries Next.js officially recommends.
- Server Actions are the canonical pattern for auth forms; Zod is the suggested validator.

## Data model (Prisma schema)

```prisma
// prisma/schema.prisma
datasource db {
  provider = "sqlite"
  url      = env("DATABASE_URL")
}

generator client {
  provider = "prisma-client-js"
}

model User {
  id            String    @id @default(cuid())
  name          String
  email         String    @unique
  passwordHash  String
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt

  addresses     Address[]
  wishlist      WishlistItem[]
  resetTokens   PasswordResetToken[]
}

model Address {
  id          String   @id @default(cuid())
  userId      String
  label       String   // "Home", "Work", etc.
  line1       String
  line2       String?
  city        String
  region      String   // state/province
  postalCode  String
  country     String   // ISO-2
  isDefault   Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

model Category {
  slug      String    @id           // e.g., "electronics"
  name      String
  image     String                  // path under /public
  products  Product[]
}

model Product {
  id            String   @id          // matches mock.ts ids ("p1", "d1") so seed is idempotent
  name          String
  price         Float
  originalPrice Float?
  image         String
  rating        Float
  reviewCount   Int
  categorySlug  String

  category      Category @relation(fields: [categorySlug], references: [slug])
  wishlistItems WishlistItem[]

  @@index([categorySlug])
}

model WishlistItem {
  id        String   @id @default(cuid())
  userId    String
  productId String
  createdAt DateTime @default(now())

  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  product   Product  @relation(fields: [productId], references: [id], onDelete: Cascade)

  @@unique([userId, productId])      // a product can't be wishlisted twice by same user
  @@index([userId])
}

model PasswordResetToken {
  id         String    @id @default(cuid())
  userId     String
  tokenHash  String    @unique         // store sha256 hash, not raw token
  expiresAt  DateTime
  usedAt     DateTime?
  createdAt  DateTime  @default(now())

  user       User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
}
```

**Decisions worth flagging:**

- **No `Account`/`Session` Prisma tables.** Auth.js v5 + Credentials requires `session: { strategy: "jwt" }`, so sessions live in a signed cookie, not the DB. The Auth.js Prisma adapter is not used; we look up users manually inside the Credentials `authorize` callback. This is the documented Auth.js pattern, not a workaround.
- **Reset tokens stored as a sha256 hash** (`tokenHash`), not the raw token. The raw token is only in the email link. Tokens expire after 30 minutes and are single-use (`usedAt`).
- **`Category.slug` is the primary key** — string PK, no synthetic id. Matches `mock.ts` shape and keeps seed idempotent.
- **`Product.id` keeps mock.ts's string IDs** ("p1", "d1") so the seed `upsert`s by id and re-running it is safe.
- **`WishlistItem` uniqueness on `(userId, productId)`** — adding the same product twice is a no-op rather than an error.
- **`onDelete: Cascade`** on user-owned tables: deleting a user removes their addresses, wishlist, and reset tokens cleanly.
- **`Float` for prices.** SQLite has no native `Decimal` type and no `@db.Decimal` mapping (`numeric` in SQLite is dynamically typed and Prisma represents it via `Float`/`Decimal` only on Postgres/MySQL). We accept floating-point rounding risk on money in the scaffold and revisit when a real payments backend lands. Downstream `ProductCard` props are plain `number`.

## SQLite + seed

No external service. The DB lives at `prisma/dev.db` (gitignored). `prisma migrate dev` creates and applies migrations against this file; `prisma db seed` populates rows.

`package.json` scripts added:

```jsonc
{
  "db:migrate": "prisma migrate dev",
  "db:seed":    "prisma db seed",
  "db:reset":   "prisma migrate reset --force"
}
```

`db:reset` uses Prisma's built-in reset (drops all tables, re-runs migrations, then `db seed`) — no Docker/file deletion needed.

`prisma/seed.ts` imports `categories`, `featuredProducts`, and `dealsProducts` from `app/_data/mock.ts`, then `upsert`s every category by `slug` and every product by `id`. Because the existing `mock.ts` `featuredProducts` and `dealsProducts` use disjoint id prefixes (`p*` and `d*`), the seed simply unions both arrays before upserting products — no dedupe logic needed.

## Auth.js configuration

Auth.js v5 requires the Edge-runtime config to be importable from the proxy without pulling in Node-only modules (`bcryptjs`, `@prisma/client`). We split the config in two:

`app/_lib/auth.config.ts` — Edge-safe; consumed by `proxy.ts`:

```ts
import type { NextAuthConfig } from "next-auth";

export const authConfig = {
  session: { strategy: "jwt", maxAge: 60 * 60 * 24 * 30 },   // 30 days
  pages: { signIn: "/login" },
  providers: [],   // populated in auth.ts (Node-only)
  callbacks: {
    authorized({ auth, request }) {
      const protectedPaths = ["/account", "/wishlist"];
      const path = request.nextUrl.pathname;
      const isProtected = protectedPaths.some((p) => path === p || path.startsWith(p + "/"));
      if (!isProtected) return true;
      if (auth) return true;
      const url = new URL("/login", request.url);
      url.searchParams.set("callbackUrl", path);
      return Response.redirect(url);
    },
    jwt({ token, user }) { if (user) token.uid = user.id; return token; },
    session({ session, token }) { if (token.uid) session.user.id = token.uid as string; return session; },
  },
} satisfies NextAuthConfig;
```

`app/_lib/auth.ts` — extends with the Credentials provider (Node-only because of `bcryptjs` + Prisma):

```ts
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";
import bcrypt from "bcryptjs";
import { prisma } from "@/app/_lib/prisma";
import { LoginSchema } from "@/app/_lib/validation";
import { authConfig } from "@/app/_lib/auth.config";

export const { handlers, signIn, signOut, auth } = NextAuth({
  ...authConfig,
  providers: [
    Credentials({
      credentials: { email: {}, password: {} },
      async authorize(creds) {
        const parsed = LoginSchema.safeParse(creds);
        if (!parsed.success) return null;
        const user = await prisma.user.findUnique({ where: { email: parsed.data.email } });
        if (!user) return null;
        const ok = await bcrypt.compare(parsed.data.password, user.passwordHash);
        if (!ok) return null;
        return { id: user.id, name: user.name, email: user.email };
      },
    }),
  ],
});
```

`app/api/auth/[...nextauth]/route.ts` re-exports `handlers.GET` and `handlers.POST` so the Auth.js HTTP endpoints are reachable.

Server-side session reads use `auth()` from `app/_lib/auth.ts` directly — RSC can `await auth()` to get `null` (guest) or `{ user: { id, name, email } }` (registered). No `useSession` is used; every UI branch on auth state happens in a server component.

## Auth flows

### Sign-up (`/signup` → `signupAction`)

1. Form posts `name`, `email`, `password`, `confirmPassword` via Server Action.
2. Validate with `SignupSchema` (Zod): name ≥ 2 chars, valid email, password ≥ 8 chars with letter + digit, password === confirmPassword.
3. Check email uniqueness via `findUnique`. If taken, return `{ error: "Email already in use" }` to `useActionState`.
4. Hash password with `bcrypt.hash(pw, 10)`.
5. `prisma.user.create({ name, email, passwordHash })`.
6. Sign in immediately: `signIn("credentials", { email, password, redirect: false })`, then `redirect("/")`.

### Log in (`/login` → `loginAction`)

1. Validate with `LoginSchema`.
2. `signIn("credentials", { email, password, redirect: false })`.
3. On `CredentialsSignin` error, return `{ error: "Invalid email or password" }` — generic, no enumeration.
4. On success, `redirect(searchParams.callbackUrl ?? "/")`.

### Log out (`logoutAction`)

`signOut({ redirectTo: "/" })`. Wired to the Log out item in the profile dropdown via a small inline `<form action={logoutAction}>` so logout works without JS.

### Forgot password (`/forgot-password` → `requestResetAction`)

1. Validate email shape.
2. Look up user. **Whether or not the user exists, return the same success state** ("If an account exists, you'll get an email"). No enumeration.
3. If user exists: generate 32 random bytes → hex token; store `tokenHash = sha256(token)` with `expiresAt = now + 30min`; send email via Nodemailer containing `${APP_URL}/reset-password?token=${rawToken}`.
4. Email send failures log to server but the action still returns success — consistent UX, no enumeration via timing.

### Reset password (`/reset-password?token=...` → `resetPasswordAction`)

1. Validate new password with `PasswordSchema`; confirm match.
2. Compute `tokenHash = sha256(submittedToken)`; look up `PasswordResetToken` where `tokenHash` matches, `usedAt IS NULL`, `expiresAt > now`.
3. If invalid/expired: error "This reset link is invalid or has expired."
4. In a transaction: update `User.passwordHash`; mark this token `usedAt = now`; invalidate all other outstanding tokens for the user (set `usedAt = now`).
5. `redirect("/login?reset=success")` — login page shows a success banner.

## Route protection

`proxy.ts` (project root) uses the Edge-safe `authConfig`. The redirect logic lives in `authConfig.callbacks.authorized`, so the proxy is just the wiring:

```ts
import NextAuth from "next-auth";
import { authConfig } from "@/app/_lib/auth.config";

export default NextAuth(authConfig).auth;

export const config = {
  matcher: ["/account/:path*", "/wishlist/:path*"],
};
```

Belt-and-suspenders: `app/account/layout.tsx` and `app/wishlist/page.tsx` *also* call `auth()` and `redirect("/login?callbackUrl=...")` if null. The proxy is the cheap first line; the layout/page check is the authoritative one (the page query needs `session.user.id` regardless).

## Account routes

### `app/account/layout.tsx` (server)

```tsx
const session = await auth();
if (!session) redirect("/login?callbackUrl=/account");

return (
  <div className="mx-auto flex max-w-7xl gap-8 px-4 py-10 sm:px-6 lg:px-8">
    <AccountSidebar userName={session.user.name} />
    <div className="flex-1">{children}</div>
  </div>
);
```

`AccountSidebar` is a small **client component** (uses `usePathname` to highlight the active item). Items: `Profile` (`/account`), `Orders` (`/account/orders`), `Addresses` (`/account/addresses`), `Security` (`/account/security`), and a separated `Log out` button at the bottom that submits `logoutAction`.

### `/account` — profile (view + edit)

- Server component fetches user.
- Form with `name` and `email` fields. `updateProfileAction` validates with `ProfileSchema`, checks email uniqueness if changed, updates the user.
- Returns `{ success: true }` or `{ error: "Email already in use" }` to `useActionState`.
- After successful update, the action calls `revalidatePath("/account")` and `revalidatePath("/")` so the header greeting refreshes.

### `/account/orders` — static mock orders

- New file `app/_data/orders-mock.ts` defining `MockOrder[]`: `{ id, placedAt, status: "delivered" | "shipped" | "processing", total, items: { productId, name, price, qty }[] }`. Six entries, varied statuses.
- Page renders order cards: id, date, status badge, total, line-item summary. Read-only.
- **Not a DB table.** Real orders land in spec #5.

### `/account/addresses`

- Server component lists `Address[]` for the current user (ordered by `isDefault DESC, createdAt DESC`).
- Each address card has `Edit` and `Delete` buttons; the default address shows a `Default` badge.
- A toggleable `Add new address` form (small client component for the toggle, reuses the same form fields as edit).
- Form fields: `label`, `line1`, `line2?`, `city`, `region`, `postalCode`, `country` (ISO-2 select), `isDefault`.
- Server actions: `addAddressAction`, `updateAddressAction(id, data)`, `deleteAddressAction(id)`, `setDefaultAddressAction(id)`. All validated via `AddressSchema`. All `revalidatePath("/account/addresses")`.
- `setDefaultAddressAction` enforces single-default invariant in a transaction:
  ```ts
  prisma.$transaction([
    prisma.address.updateMany({ where: { userId }, data: { isDefault: false } }),
    prisma.address.update({ where: { id }, data: { isDefault: true } }),
  ]);
  ```
- Every action verifies ownership (`address.userId === session.user.id`) before any write — defense against id-tampering.

### `/account/security`

- Single form: `currentPassword`, `newPassword`, `confirmPassword`.
- `changePasswordAction`: verify `currentPassword` against `passwordHash`, validate new password with `PasswordSchema`, confirm match, hash new password, update.
- Returns success/error to `useActionState`.

## Wishlist

### `/wishlist` (server)

- `auth()` check + `redirect("/login?callbackUrl=/wishlist")` if guest. (Proxy already covers this; layout/page check is authoritative.)
- Fetches `WishlistItem[]` joined to `Product` for the current user, ordered by `createdAt DESC`.
- Renders the same `ProductCard` grid used on the home page, with a `Remove` button per card (heart-filled icon → submits `removeFromWishlistAction(productId)`).
- Empty state: heading "Your wishlist is empty", subtext, `Button` linking to `/`.

### Heart-toggle on `ProductCard`

`ProductCard` stays a server component. The heart button is a `<form>` whose action is `toggleWishlistAction(productId)`:

1. If guest: action returns `redirect("/login?callbackUrl=...")`.
2. Otherwise: toggle the row using the `(userId, productId)` unique constraint — insert if missing, delete if present.
3. `revalidatePath("/")` and `revalidatePath("/wishlist")` so the heart's filled/empty state updates wherever this product appears on the next render.

The form submit also includes a hidden `pathname` field so the action knows which page to revalidate; if more product-listing pages are added later (e.g., a product detail page), include them in the same `revalidatePath` call. No client component is needed. Works without JS. Trade-off: the page re-renders rather than doing optimistic UI — fine for scaffold scope.

To know whether to render the heart filled, server pages that render a `ProductCard` pass an extra prop `wishlistedProductIds: Set<string>` (fetched once per page render via `getWishlistProductIds(userId)`; returns `Set` so card lookup is O(1)). For guests, the set is empty and every heart is unfilled.

## Verification

This is still a scaffold round; behavior verification is largely manual.

**Automated:**

1. `npm run lint` passes.
2. `npm run build` succeeds with no type errors.
3. `npx prisma validate` passes; `npx prisma migrate dev --name init` runs cleanly against the dockerized Postgres; `npx prisma db seed` populates products + categories.

**Manual happy paths:**

4. `npm run dev`. Home page renders with all sections fed from SQLite (products and categories visible, deals carry discount badges).
5. Header shows Search → Wishlist → Cart → Profile. As guest: profile dropdown shows Log in / Sign up; clicking the wishlist icon redirects to `/login?callbackUrl=/wishlist`.
6. Sign up via `/signup` (name + email + password + confirm). Successful signup logs you in and redirects to `/`. Header now shows registered dropdown ("Hi, …" + account links + Log out).
7. From a product card, click the heart → card re-renders with filled heart. Visit `/wishlist` → product appears. Click "Remove" → product gone, heart empties on the home page.
8. Visit `/account`: sidebar visible; profile form edits name/email; saved name appears immediately in the header dropdown.
9. `/account/addresses`: add an address, mark it default, edit, delete. Default invariant holds.
10. `/account/orders`: shows the static mock orders.
11. `/account/security`: change password with wrong current password → error. With correct current password → success; old password no longer logs you in; new password does.
12. Log out via dropdown → redirected to `/`; header reverts to guest state.
13. Forgot-password loop with SMTP configured: submit email → message sent; click link → reset page accepts new password; old token can't be reused; expired token (manually shifted) is rejected.
14. Direct-URL probe: `/account` and `/wishlist` while logged out → redirected to `/login?callbackUrl=…`. After login, redirected back to the original URL.
15. Hydration: no console errors or warnings on any page; light/dark and mobile/tablet/desktop unchanged from the existing scaffold.

**Security spot-checks:**

- Login error messages are identical for "no such email" vs "wrong password" (no enumeration).
- Forgot-password returns the same response for known and unknown emails.
- Address actions on addresses owned by another user (manually crafted form post) are rejected before any mutation.
